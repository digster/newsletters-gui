# 2026-08-29: Fix Latent Data Corruption in the Email Index

## The bug

`emails.id` was the email folder name (`scan.rs:89`), declared `id TEXT PRIMARY KEY` and
written with `INSERT OR REPLACE`. Folder names were 8-char truncations of the Gmail
message ID — which collide, and legitimately repeat across labels. Three consequences:

1. Colliding pairs overwrote each other in the index.
2. `existing_state` restored `is_read`/`is_bookmarked` on the same key, so **user state
   bled between unrelated newsletters in different labels**.
3. `scan.rs:101-102` picked the first `*.html` in `read_dir` order — non-deterministic
   across machines and rescans, and it discarded any other `.html` in the folder.

## What was done

- **Split identity into three columns** (`db.rs`): `id` = `"<label>/<message_id>"`
  (primary key + frontend handle), `dir_name` = on-disk folder (path building only),
  `message_id` = full Gmail ID. Added `UNIQUE INDEX idx_emails_identity
  (label, dir_name, html_filename)` — one row per physical `.html`.
- **`message_id` resolution order**: front matter `id:` → `.html` filename stem (when it
  looks like a hex message ID) → folder name. Every fallback is unique within a label.
- **Schema centralized** into `db.rs` constants (`EMAILS_TABLE_SQL`, `EMAILS_INDEX_SQL`,
  `FTS_TABLE_SQL`) so migration, re-index, and tests can't drift.
- **In-place migration** for existing databases: `dir_name = id`, then
  `id = label || '/' || id`, guarded by `instr(id,'/') = 0` so it's idempotent. Existing
  bookmarks survive the upgrade.
- **`scan.rs` rewritten**: pure, testable `scan_newsletters()` / `insert_chunk()` /
  `ExistingState`, separate from the Tauri command. Fully sorted traversal at every level.
  One `ParsedEmail` per `.html` file, each paired to its `.md` by front-matter ID, then by
  filename embedding, then by one-body-one-sidecar elimination.
- **`ExistingState`** keyed by uid with a `(label, dir_name, html_filename)` fallback —
  both label-scoped, so bleed is impossible by construction.
- **`INSERT OR REPLACE` → `INSERT`**, and FTS rowid now from `conn.last_insert_rowid()`
  instead of re-querying by id (which could resolve to the wrong row under collisions).
- **`parser.rs`**: added `Frontmatter.id` using the lenient scalar deserializer (all-digit
  IDs parse as YAML integers — gmail-ingestor LEARNINGS).
- **`emails.rs`**: `get_email_html` builds the path from `dir_name`, never from `id`.
- **`email-list.js`**: escape quotes/backslashes in the `data-email-id` attribute selector
  now that ids embed arbitrary label text.

## Verification

- 31 Rust tests pass (14 new), including the required regression: two folders named
  `1786999a` under different labels index as two distinct rows, with and without front
  matter IDs, and state restore does not cross labels.
- Real corpus (`../newsletters`): 16,606 emails scanned in 1.03s, 16,606 distinct uids,
  0 duplicates, 0 missing files on path re-resolution, 68 labels, insert in 785ms.
- Live database copy migrated cleanly: 13,636 rows all promoted to composite ids with
  `dir_name` preserved (e.g. `id="River Kenna/19504111"`, `dir_name="19504111"`).
- `cargo build --release` clean, no warnings.

## Notes / follow-ups

- The corpus has already been rebuilt with full 16-char folder names, so no collisions
  exist on disk *today*. The fix is deliberately independent of that.
- **400 folders hold plain-text-only emails** (`.txt` + `.md`, no `.html`) and are skipped
  — pre-existing behaviour, not a regression. Supporting them needs a nullable
  `html_filename` and a text path in the viewer.

# 2026-08-29: Index Plain-Text-Only Newsletters (follow-up to the finding above)

## The gap

400 emails (all under the `Quincy` label) ship no HTML part — the folder holds only a
`.txt` and a `.md`. The scanner required an `.html`, so those emails were never indexed
and were invisible in the app. The schema encoded the assumption: `html_filename TEXT NOT
NULL` could not name anything else.

## What was done

- **`html_filename` → `body_filename`, plus `body_format` ('html' | 'text')** (`db.rs`).
  `ALTER TABLE ... RENAME COLUMN` migrates existing databases and SQLite rewrites the
  column reference inside `idx_emails_identity` automatically. Kept NOT NULL deliberately:
  a nullable column would have silently disabled the unique identity index, since SQLite
  treats NULLs as distinct.
- **Identity-based body selection** (`scan.rs`, `scan_email_dir` now three passes):
  1. every `.html` is a body;
  2. a `.txt` is promoted only when the *message* it names has no HTML body — always if
     the folder has no `.html`, otherwise only when its stem is a message ID that no HTML
     body resolved to (the colliding-pair-without-HTML shape);
  3. keys assigned and rows emitted.
  Filename-based rules would either double-count every email (a `.txt` sits beside almost
  every `.html`) or drop the HTML-less member of a colliding pair.
- Extracted `resolve_body()` so HTML and text bodies share one md-matching and
  message_id-resolution path.
- **`get_email_html` renders text bodies**: escaped and wrapped in `<pre>` inside a minimal
  document, in Rust, because the string goes straight into an iframe `srcdoc`. The wrapper
  sets no colours — the viewer's `color-scheme` injection makes the UA default text colour
  follow the theme in both light and dark.
- Search tests now build their schema from the `db.rs` constants instead of a private copy.

## Verification

- 39 tests pass (8 new): text-only indexed with `body_format='text'`; a `.txt` beside an
  `.html` is **not** double-indexed (both ID-named and legacy generic naming); an
  HTML-less message in a shared folder **is** promoted; a `.txt` matching the html's
  front-matter ID is not; text-only state survives re-index; body escaping and document
  structure.
- Real corpus: **17,006 emails** (was 16,606) = exactly the 17,006 folders on disk.
  16,606 html + 400 text, 17,006 distinct uids, 0 duplicates, 0 missing files, 723ms scan.
  A text-only email is reachable via FTS.
- Live database copy (with WAL): 13,636 rows migrated, all composite ids, all
  `body_format='html'`, user state preserved.
- Rendering verified visually in a browser in both light and dark themes using a real
  `Quincy` .txt through the actual `render_text_body` path.
- `cargo build --release` clean, no warnings.

## Measured facts worth keeping

- Across 16,606 folders with HTML, **zero** have a `.txt` whose stem doesn't match an
  `.html`. The promotion path guards a known bug class; it is not a live case today.
- All 400 text-only folders are exactly (1 .txt, 1 .md) and all sit under one label.
